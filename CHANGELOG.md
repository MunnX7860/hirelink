### Added — Phase 5 · Smart Screening (Stage 5.4 — async large pools, 2026-08-09)

**Screening sessions now run to completion with no browser open: a per-minute cron worker, a crash-proof processing lease, quota auto-resume, and a Gemini Batch accelerator for pools ≥ 50 (separate quota, ~50 % cost) that falls back to the chunked engine seamlessly on ANY failure. Failed candidates retry individually; in-flight sessions can be stopped — 7 of 500 failing never fails the run.**

- **Processing lease (migration 0008, 17 §9.1)**: `ai_screening_sessions.locked_at` + partial `screening_sessions_active_idx` (active statuses only). Every advancer — create-kickoff, cron, advance-on-view — CAS-claims on the exact observed lock (`isLeaseClaimable` pure predicate guard-tested); a clean slice releases to `null`, a crash is reclaimed after the 10-min expiry, and `quota_limited` keeps the fresh lock as a 2-min cooldown marker (auto-resume). Double-processing is impossible by construction.
- **Cron worker (`GET /api/cron/screening-worker` + `vercel.json` `* * * * *`)**: mirrors the org-purge/reconcile pattern (404 without `CRON_SECRET`, 401 on wrong bearer, service client in the allowed zone, 17 §10); scans ≤10 active sessions, CAS-claims ≤3, advances each one ≤50 s slice within a 45 s budget; per-sessions crashes are absorbed into the tick result. docs/12 already documents the paid-plan cadence + Hobby fallback note.
- **Advance-on-view (17 §9.1)**: `GET /api/ai/screenings/:id` kicks one post-response slice via `after()` while the session is active — the dashboard's existing 3 s polling becomes the Hobby self-healer; race-safe via the same CAS lease.
- **Gemini Batch accelerator (17 §9.2, `lib/ai/batch.ts` + `features/screening/batch-session.ts`)**: pending pool ≥ 50→ one Batch job with one prompt per candidate (same packed anonymized blocks as the interactive engine; `metadata.key` = result row id so drain-time correlation never trusts labels). Plain-REST client in the docs/10 posture (key in header never URL; 401/403 → integration banner, 400-class → `ai_batch_unsupported` fallback signal, 429/5xx/network retryable); BOTH documented poll-resource shapes (`metadata.state`+`response.inlinedResponses` / `state`+`dest.inlinedResponses`) normalized; inline-only with a 15 MB guard (file mode deliberately deferred). Running → live counters from `batchStats`; SUCCEEDED → tolerant per-row drain with the §8 safe rails (`parseBatchItemResult` heals the advisory label, clamps score, unknown category → `review_required`); FAILED/EXPIRED/CANCELLED → rows stay pending and the interactive engine takes over. Upgrade decision uses the REAL pending volume, so a retried 500-pool with 3 failed rows never re-batches 3 items.
- **Retry + cancel (05 §4.10, 17 §9.3)**: `POST /api/ai/screenings/:id/retry` flips only `failed` rows back to `pending`, revives the terminal session (engine provenance reset to `interactive`), resumes key-broken sessions whose rows are still pending (`resumed` count), 202 when work remains / honest 200 no-op otherwise / 409 while running, and kicks processing in `after()`. `POST /api/ai/screenings/:id/cancel` stops `queued`/`processing`/`quota_limited` sessions, cancels a live Batch remotely best-effort (D4), retains completed rows; 409 when terminal. Dashboard gains **Retry N failed / Resume** + **Stop** (two-tap confirm, mobile-first) buttons and a **Batch** badge on accelerated sessions.
- **Tests**: +26 unit → **342** (lease/cooldown/retry/cancel/upgrade predicates, single-result JSON-schema mirror, 0008 SQL sanity; batch create-body shape, create/poll/cancel over fake transport incl. both resource shapes + failure classification, salvage-first item parser) + 3 always-on e2e → **61** (retry/cancel 401 rows, cron-bearer gate). Gates: tsc/eslint/prettier clean, build green (`/apply/[slug]` unchanged 5.63 kB; screening page 8.02 kB).
- **Deferred to 5.5 by design**: results polish + optional Drive `AI Screenings/` summary artifact (17 §13).

- **Processing kickoff**: `after()` right after the 201 (same-pattern as notifications), `maxDuration = 60`; progress persisted per chunk (`processed/failed` counters) so the UI shows live advancement. Small pools (≲50) complete inside one kickoff.
- **`screen_candidates.v1` prompt + `ScreeningResultSchema`** (17 §8): guardrails 1–3 + screening non-negotiables 4–6 (inert blocks, evidence-only with INSUFFICIENT_EVIDENCE vocabulary, fewer-than-N always acceptable — standard never lowered); heals on the safe rail (unknown category → `review_required`, score clamped int 0–100 or null, lists sliced/word-capped) and rejects true contract violations; job context assembled server-side incl. mandatory expectations as plain language (`describeRule`).

### Added — Phase 5 · Smart Screening (Stage 5.1 — questionnaire + deterministic engine, 2026-08-09)

**HireLink can now attach a screening questionnaire to a job and compute a deterministic verdict (QUALIFIED / DOES_NOT_MEET_MANDATORY / REVIEW_REQUIRED) the moment a candidate applies — with the safety rail that anything ambiguous is sent to a human, never auto-rejected. Works with ZERO AI configured. Verdicts live on their own `applications.screening_status` column — the pipeline status stays human-owned.**

- **Migration 0007** (additive, re-runnable): `jobs.screening_config` jsonb (`{"questions":[]}` default — PRIVATE rules, never projected to `form_config`), `applications.screening_status` check-constrained to the three verdicts (NULL = feature off), `timeline_event_type` + `'questionnaire_screened'`, and four new tables with full RLS: `application_answers` (unique question-per-application, read-only owner/org policies — writes are service-only from the public apply path), `applicant_profiles` (parse-v2 cache, 1:1 with applicant; consumed in Stage 5.2), `ai_screening_sessions` + `ai_screening_results` (append-only AI history; consumed in Stage 5.3+), plus listing indexes incl. `applications(job_id, screening_status)`.
- **`features/screening/schemas.ts`**: 12 question types, 3 classifications; cross-field refinements (mandatory ⇔ rule coupling, operator-per-type matrix, options 2–12 + unique for choice types, optioned rule values ⊆ options, range needs ≥1 bound); `sanitizeQuestions()` is the ONLY projection allowed to candidates (strips `rule`/`classification` — Q7 leak guarantee); `validateAnswers()` types/cleans the apply payload (numeric strings tolerate `₹ $ ,` and spaces), drops unknown ids, and returns field errors keyed `answers.<question_id>`.
- **Pure deterministic engine** (`features/screening/engine.ts`): every type×operator; aggregation = any clear fail → DNMC, else any ambiguous/empty/unknown-option → review_required, else qualified; no mandatory questions → NULL. 100 % branch-covered per docs/13.
- **Apply integration** (docs/17 §5): apply payload accepts an `answers` JSON field (≤8 KB) on the existing multipart post; validation failures → 400 `VALIDATION_ERROR` with the standard `details` map; answers + verdict + timeline event persist **after** the application row exists, with failures absorbed (D4 — screening can never block a submission); first-write-wins (idempotent re-applies don't touch answers). Public job route now includes sanitized `questions`; apply page renders all 12 field types (radio pills, checkboxes, selects, numeric inputs) inside the 60 KB budget — `/apply/[slug]` now 5.63 kB first-load.
- **Recruiter surfaces**: questionnaire builder on the job edit page (add/reorder/remove, classification, rule editor per type, "Re-run screening for existing applications" — synchronous recompute, changed verdicts journaled, history untouched otherwise); application detail gains an **Answers & screening** card (verdict badge + per-question answers with type-aware formatting).
- **Routes** (05 §4.10 subset): `GET/PUT /api/jobs/:id/screening-config` (`jobs.write`), `POST /api/jobs/:id/screening-recompute` → 200 `{recomputed, changed}`, `GET /api/applications/:id/answers` (scope-verified via parent job, 404 on mismatch).
- **Tests**: +31 engine unit +66 schema/migration unit → **281 unit**; +5 always-on e2e (`e2e/screening-api.spec.ts` 401-envelope matrix + Q7 public-payload leak check) → **53 always-on**. Gates held: tsc/lint/prettier clean, build green (≈60 routes).
- **Deviations from the 5.0 docs (deliberate, docs amended)**: recompute endpoint is **synchronous** 200 `{recomputed, changed}` (pure engine, DB-bound) rather than worker-queued 202 — docs/05 §4.10 + docs/17 §4.4 updated to match; radios on the apply form dropped `aria-invalid` (unsupported on the radio role — error is announced via the aria-live error line).
